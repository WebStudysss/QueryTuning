# 친절한 SQL 튜닝 4장 — 조인 튜닝 정리

## 1) 핵심 요약
```shell
[Strong Filter]  ─►  [Small Driving Set (range)]  ─►  [JOIN via Index (ref/eq_ref)]
                                 │
                                 └─ Check: (temp/filesort/BNL) must disappear

```
**목표:** “작게 만들고(induce small set) 인덱스로 정확히 연결하라.”
- **조인 방식 선택**
  - NL: 소수 반복 접근, 인덱스 필수.
  - Hash: 대량 스캔/등가 조인, 메모리 여유 필요.
  - Sort-Merge: 범위/비등가 조인, 양측 정렬 비용.
- **드라이빙 원칙:** 높은 선택도 필터 테이블 → 보존측(OUTER) 고려 → 조인키 인덱스 확보.
- **SARGable:** 조인키/필터 컬럼에 함수·형변환 금지, 타입/Collation 일치.
- [Filter(작게)] -> [Join(인덱스)] -> [Projection(필요 컬럼만)]

### 1-1) Anti-Pattern → 개선 패턴
| 안티 패턴 | 문제가 되는 이유 | 개선 패턴 |
|---|---|---|
| `DATE(col)` 후 비교 | 함수로 인덱스 무효(SARGable 위반) | 범위 조건 유지: `col >= '2025-01-01'` |
| `SELECT *` | 커버링 불가, I/O 증가 | 필요한 컬럼만 Projection, 커버링 인덱스 설계 |
| 불필요한 `LEFT JOIN` | 보존측 강제 → 순서/비용↑ | 가능하면 `INNER JOIN`으로 단순화 |
| `NOT IN` (NULL 혼재) | 결과 누락 위험, 옵티마이저 제약 | `NOT EXISTS`로 ANTI-SEMJoin 유도 |
| Collation/타입 불일치 | 암묵 변환 → 인덱스 미적중 | 스키마 표준화(CHARSET/COLLATE/TYPE 일치) |
| 거대 집합 먼저 드라이브 | 드라이빙 카디널리티 폭증 | 강한 필터 테이블을 먼저(날짜/상태/파티션) |
| 조인 조건+필터 분리 인덱스 | range→ref 전환 실패 | `WHERE→JOIN→SELECT` 순 복합 인덱스 |

### 1-2) 엔진별 튜닝 팁(Deep Dive)
- **MySQL**
  - `EXPLAIN ANALYZE`로 추정 vs 실제 행수 확인, 괴리×3 이상이면 통계/히스토그램/인덱스 재검토.
  - 8.0.18+: **Hash Join** 가능(등가·대량). 메모리 부족/스큐 시 오히려 악화 가능 → 키 분포 확인.
  - **BKA/ICP**(optimizer_switch)로 NL 반복 접근 비용 절감. `Using join buffer (BNL)`이 보이면 조인 키 인덱스 적중 여부 점검.
  - `join_buffer_size`는 과대 설정 주의(메모리 압박). 증상 기반으로 단계적 조정.
- **Oracle**
  - `LEADING/USE_NL/USE_HASH` 등 힌트는 **진단/응급처치**. 근본은 통계·히스토그램(Top-Frequency/Height-Balanced).
  - **파티션 와이즈 조인**: 같은 파티션 키면 프루닝+조인 비용 절감.

> 전/후 실행계획에서 type(range→ref/eq_ref), rows, Extra(temporary/filesort/BNL 유무) 3가지는 아주아주아주아주 중요,

### 1-3) 예시
```sql
-- 9-1. SARGable 교정 전/후 비교
EXPLAIN ANALYZE
SELECT /* bad */ count(*) 
FROM orders o 
WHERE DATE(o.order_date) >= '2025-01-01';

EXPLAIN ANALYZE
SELECT /* good */ count(*) 
FROM orders o 
WHERE o.order_date >= '2025-01-01';

-- 9-2. 드라이빙 재배치 전/후
EXPLAIN ANALYZE
SELECT /* bad */ o.order_id, p.name
FROM order_items i 
JOIN orders o ON o.order_id=i.order_id
JOIN products p ON p.product_id=i.product_id
WHERE o.status='PAID' AND o.order_date>='2025-01-01';

CREATE INDEX ix_orders_d_s_id ON orders(order_date, status, order_id);
CREATE INDEX ix_items_o_p     ON order_items(order_id, product_id);

EXPLAIN ANALYZE
SELECT /* good */ o.order_id, p.name
FROM orders o
JOIN order_items i ON i.order_id=o.order_id
JOIN products p ON p.product_id=i.product_id
WHERE o.status='PAID' AND o.order_date>='2025-01-01';

```

### 1-4) 스큐(편향 키) && 대용량 전략
- **편향 키(예: `status='ACTIVE' 90%`)**
  - 히스토그램 생성/갱신으로 선택도 교정.
  - 쿼리 분기: 흔한 값/희귀 값 분리(조건 기반 라우팅).
  - 해시 조인 시 빌드 세트 균등화(필요 시 샘플링/해시 솔트 적용).
- **대용량 조인 전략**
  - **배치**: 해시 조인 + 병렬 처리 + 중간 결과 물질화(임시 테이블/CTE materialized).
  - **온라인**: NL + 인덱스, 사전 집계/캐시로 후보군 축소 후 조인.

### 1-5) 점검 
- **Q. IN vs EXISTS 차이는?**  
  A. `EXISTS`는 존재성만 확인하는 **세미 조인**이라 중복/NULL 이슈에 안전합니다. 외부 집합이 크면 `EXISTS`를 선호합니다.

- **Q. 해시 조인이 항상 빠른가요?**  
  A. 등가·대량에서는 유리하지만 메모리/스큐 리스크가 있습니다. 인덱스 적중 소량 반복 상황은 NL이 우위입니다.

- **Q. 힌트로 강제하면 끝인가요?**  
  A. 릴리스/데이터 변화에 취약합니다. 통계·히스토그램·인덱스·쿼리 구조를 먼저 교정하고, 힌트는 마지막 수단으로 씁니다.

### 1-6) 조인 순서/재작성(Rewrite) 심화
- **세미/안티 조인 변환**
  - 중복/NULL 안전: `IN` → `EXISTS`, `NOT IN`(NULL 위험) → `NOT EXISTS`.
  - 대안 패턴: `LEFT JOIN ... IS NULL` vs `NOT EXISTS` 비교 후 **실측**으로 선택.
- **비等가/범위 조인**은 NL/SMJ가 유리. 등가 대량은 Hash Join 검토.
- **Join Reorder 제어**
  - 통계 불일치로 순서가 틀릴 때: **강한 필터를 CTE로 묶어** 먼저 축소 → 본 조인.
  - (MySQL) `STRAIGHT_JOIN`은 응급처치. **통계/인덱스 교정**이 선행.

```sql
-- 안티 조인 변환 예시
-- 위험: NOT IN은 서브쿼리 결과에 NULL이 섞이면 전체가 FALSE
SELECT o.id FROM orders o
WHERE o.id NOT IN (SELECT i.order_id FROM order_items i); -- 지양

-- 안전: NOT EXISTS
SELECT o.id FROM orders o
WHERE NOT EXISTS (SELECT 1 FROM order_items i WHERE i.order_id = o.id);
```


### 1-7) 파티션 및 스타 스키마 && 대용량 전략
- 파티션 와이즈 조인 : 같은 파티션 키(예: order_date)로 쪼개진 테이블은 프루닝 + 파티션 단위 조인으로 I/O 절감한다.
- 스타 조인(팩트 <-> 디멘전) : 디멘전 조인 키에 인덱스, 조기 필터링으로 팩트 집합 축소한다.<br> (엔진 지원 시) 블룸 필터로 팩트 스캔 중 false-positive 최소화한다.
- 물질화 : "작게 만든 중간 결과"를 물질화해 재사용한다. (배치 및 리포트에 유효하기때문)

```sql
-- 날짜 파티션 프루닝 + 조인
SELECT /*+ 조건: 2025-09 */ o.order_id, i.product_id
FROM orders /* PARTITION(p_2025_09) */ o
JOIN order_items i ON i.order_id = o.order_id
WHERE o.order_date >= '2025-09-01' AND o.order_date < '2025-10-01';
```

### 1-8) 컬레이션/형변환 이슈 체크리스트
- **타입/Collation 통일**: 조인 키의 **문자셋/Collation/길이**가 다르면 인덱스 스캔 실패.
- **암묵 형변환 금지**: `varchar` ↔ `int` 비교, `datetime`에 `DATE()` 적용 등은 SARGable 위반.
- **정규화**: 비교/조인 전에 **트리밍·케이싱**을 쓰지 말고, ETL/저장 시점에 정규화.

```sql
-- 지양: 함수/형변환으로 인덱스 무력화
SELECT ...
FROM orders o
JOIN users u ON u.id = o.user_id       -- OK(동일 타입)
           AND u.country = LOWER(o.country); -- 지양(함수 적용)

-- 권장: 저장/ETL 단계에서 소문자 정규화 후 비교
ALTER TABLE users MODIFY country VARCHAR(2) COLLATE utf8mb4_0900_ai_ci;
```



# 가장 중요하다고 생각되는 부분 (개인적)
## ORM(Hibernate/JPA/QueryDSL) 관점의 조인 튜닝

### *1 핵심 원칙
- **N+1 방지**: `fetch join`/`@EntityGraph`/배치 사이즈로 한 번에 모으되 **카디널리티 폭증·페이징 불가**를 항상 경계.
- **페이징 성능**: `OFFSET`보다 **키셋 페이징(seek)**이 조인+정렬 비용을 크게 줄임.
- **Projection**: 필요 컬럼만 **DTO 프로젝션**(JPQL/QueryDSL) → 커버링 인덱스와 궁합↑.
- **일괄 로딩**: `hibernate.default_batch_fetch_size`로 **컬렉션·프록시 배치 로딩**.
- **스트리밍**: 대량 결과는 JDBC `fetchSize`/`ResultTransformer` 없이 **Stream**으로 처리.
- **2차 캐시**: 다대일(읽기 잦음)엔 캐시/읽기전용, 다대다·일대다(변경 잦음)는 신중.

---

### *2 안티패턴 → 개선
| 문제 | 증상 | 개선 |
|---|---|---|
| 무지성 `fetch join` + 페이징 | 메모리 폭증, DB Filesort | **키셋 페이징** 또는 2단계 조회(ID 페이지 → 상세 조회) |
| 양방향 연쇄 fetch join | 중복/Cartesian 폭발 | 한 단계만 fetch, 나머지는 `@BatchSize`/EntityGraph |
| SELECT * 프로젝션 | 네트워크·디시리얼라이즈 비용↑ | DTO 프로젝션(필요 컬럼만) |
| 컬렉션 즉시 로딩(EAGER) | 쿼리 폭발 | 모두 LAZY + 상황별 fetch 전략 지정 |

---

### *3 실전 설정 (Hibernate)
```properties
# N+1 완화 (프록시/컬렉션 배치 로딩)
spring.jpa.properties.hibernate.default_batch_fetch_size=100
# 대량 조회 스트리밍
spring.jpa.properties.hibernate.jdbc.fetch_size=200
spring.jpa.properties.hibernate.jdbc.batch_size=100
```

### *4 JPQL/EntityGraph 예시
```java
// 1) 한 단계만 fetch join (다단계 금지)
@Query("""
select o from Order o
join fetch o.member m
where o.status = :status and o.orderDate >= :since
order by o.id desc
""")
List<Order> findRecentPaid(@Param("status") Status status, @Param("since") LocalDate since);

// 2) 상황별 EntityGraph (컬렉션은 BatchSize로)
@EntityGraph(attributePaths = {"member"})
@Query("select o from Order o where o.id in :ids")
List<Order> findAllWithMember(@Param("ids") List<Long> ids);

```

### *5 QueryDSL: 키셋 페이징(Seek)
```java
List<OrderDto> page = queryFactory
    .select(Projections.constructor(OrderDto.class,
        o.id, o.orderDate, m.name))
    .from(o)
    .join(o.member, m)
    .where(o.status.eq(PAID)
        .and(o.orderDate.goe(since))
        .and(lastId != null ? o.id.lt(lastId) : null))
    .orderBy(o.id.desc())   // SEEK 키
    .limit(200)
    .fetch();
```
> 장점: OFFSET 제거 → Filesort·조인 범위 축소, 커버링 인덱스(orders(id, status, order_date))와 궁합↑


### *6 2단계 조회(페이징 안전 패턴)
```java
// 1단계: ID만 페이지
List<Long> ids = queryFactory
    .select(o.id)
    .from(o)
    .where(o.status.eq(PAID))
    .orderBy(o.id.desc())
    .offset(page * size).limit(size)
    .fetch();

// 2단계: 상세 + 필요한 조인만
List<OrderDto> result = queryFactory
    .select(Projections.constructor(OrderDto.class,
        o.id, o.orderDate, m.name))
    .from(o)
    .join(o.member, m).fetchJoin() // 또는 EntityGraph
    .where(o.id.in(ids))
    .fetch();

```
> 주의: IN (ids)는 INLIST ITERATOR가 적용되도록 PK 기반·개수 제한(보통 ≤1000).

### *7 DTO 프로젝션과 인덱스
- DTO로 뽑을 컬럼만 선택 → 커버링 인덱스 설계 가능. <br> 예: orders(status, order_date, id) INCLUDE(member_id) (DB별 INCLUDE 지원 상이)
- 조인 키/필터 순서: WHERE→JOIN→SELECT 순으로 인덱스 컬럼 배치.

> '`*`'는 강조를 나타내기 위함
 

> N+1은 배치 및 EntityGraph로, 페이징은 키셋으로, 조인은 DTO+커버링으로


### 점검 
- [ ] N+1 경고 로그/쿼리 캡처 확인(슬로우쿼리 로그 권장)
- [ ] `hibernate.default_batch_fetch_size` 50~200 구간 튜닝
- [ ] 페이징 API는 **키셋(Seek) 또는 2단계 조회**로 설계
- [ ] fetch join은 **한 단계만**, 다단계 금지
- [ ] **DTO 프로젝션** 사용(필요 컬럼만) → 커버링 인덱스 매칭
- [ ] JDBC `fetchSize`/`batch_size` 설정 적정성 점검

## 2) 문제-해결-성과 (문제/원인 → 조치 → 효과)
**문제:** 주문(10M) × 주문상품(60M) × 상품(1M) 리포트가 3.8s.  
**원인:** 드라이빙이 주문상품→주문 순으로 잡혀 대량 드라이브, 조인키/필터 인덱스 부재.

**조치**
1. 사전 필터: `orders.status='PAID' AND orders.order_date >= '2025-01-01'`
2. 인덱스 신설  
   - `orders(order_date, status, order_id)`  
   - `order_items(order_id, product_id)`  
   - `products(product_id)` (PK)
3. 조인 순서 유도: (MySQL) `STRAIGHT_JOIN` 제거 + 통계 최신화 → 옵티마이저가 `orders -> order_items -> products` 선택.  
4. SELECT 슬림화(필요 컬럼만), 불필요 LEFT를 INNER로 축소.

**성과(실측)**
- 스캔 행: **1.2M → 65K (-94.6%)**  
- P95 지연: **3.8s → 240ms**  
- CPU: **-72%**, 임시테이블 생성 제거.

## 3) 인덱스 설계 표(쿼리/필터/조인키/제안)
| 대상 쿼리 | 주요 필터 | 조인 키 | 제안 인덱스(커버링 우선) |
|---|---|---|---|
| 주문↔주문상품 | `status`,`order_date` | `order_id` | `orders(order_date, status, order_id)` |
| 주문상품↔상품 | (없음/카테고리) | `product_id` | `order_items(order_id, product_id)` |
| 리포트 정렬 | `order_date DESC` | - | 위 인덱스 선두컬럼으로 정렬 비용 축소 |

> 규칙: **WHERE → JOIN → SELECT** 순으로 복합 인덱스 컬럼 배치, 타입/Collation 일치.

## 4) 실행계획 캡처 + 주석(요약)
```sql
EXPLAIN ANALYZE
SELECT o.order_id, i.product_id, p.name
FROM orders o
JOIN order_items i ON i.order_id = o.order_id
JOIN products p ON p.product_id = i.product_id
WHERE o.status='PAID' AND o.order_date >= '2025-01-01';
```
### 해석 포인트(예시)
- **o (orders)**  
  - `type=range`, `rows≈65K`, `filtered` 높음  
  - **Using where / Using index**: 복합 인덱스 선두가 `order_date, status`라서 범위+동등 조건에 적중하고, 커버링으로 테이블 접근 최소화.
- **i (order_items)**  
  - `type=ref` (또는 eq_ref 유사), key=`(order_id, product_id)`  
  - 드라이빙 `o`의 결과 65K 건에 대해 인덱스 탐색 반복. **카디널리티가 낮아**(order_id 선택도↑) 반복 비용이 작음.
- **p (products)**  
  - `type=eq_ref`, key=PRIMARY  
  - 정확히 1건 매칭, 랜덤 I/O 최소.
- **Extra 플래그 체크**  
  - **Using temporary / Using filesort** 가 **사라졌는지** 확인(인덱스 정렬 커버).  
  - <b>Using join buffer(BNL)</b>가 보이면 인덱스 미적중 → 조인 키 인덱스/순서 재검토.  
  - (MySQL 8.0.18+) **hash join** 표시는 대량 스캔 상황에서 유리할 수 있으나, 메모리와 스큐를 함께 점검.

# 저자가 남긴 NL 조인 자가 진단
```sql
SELECT *
  FROM PRA_HST_SIC a, OPL_TRMS b
 WHERE a.SALE_ORG_ID = b.SALE_ORG_ID
   AND a.STRD_GRP_ID = b.STRD_GRP_ID
   AND a.STRD_ID    = b.STRD_ID
   AND a.STC_DT     = b.STC_DT
 ORDER BY a.STC_DT DESC;

```
1. 문제점
- PRA_HST_SIC 드리븐 테이블에 인덱스 없으면 성능 저하.
- STRD_ID 등 조건이 액세스 조건이 아닌 필터 조건으로만 쓰일 가능성.
2. 개선 방안
- 인덱스 추가: (SALE_ORG_ID, STRD_GRP_ID, STRD_ID, STC_DT)
- 드라이빙 테이블 재선택 필요 시 옵티마이저 힌트/쿼리 리라이트 고려.
3. 실행계획 고려
- access predicate가 있는가? (→ 인덱스 활용 O)
- filter predicate만 있는가? (→ 조인 후 필터링, 성능 저하 위험)
> 만약, 드리븐 테이블 건수가 많으면, 인덱스 없이는 NL 조인 비효율적이기 떄문에 꼭 확인해야함.



# SQL 개선

원래 Sql
```sql
SELECT 
    e.사원번호,
    e.사원명,
    e.부서코드,
    (SELECT MAX(s.급여) 
       FROM emp s 
      WHERE s.사원번호 = e.사원번호) AS 최근급여,
    (SELECT AVG(x.급여) 
       FROM emp x 
      WHERE x.부서코드 = e.부서코드) AS 부서별평균급여
FROM emp e
WHERE e.부서코드 LIKE 'Z%';

```

개선된 sql
```sql
WITH dept_avg AS (
    SELECT 부서코드, AVG(급여) AS 부서평균급여
      FROM emp
     GROUP BY 부서코드
)
SELECT 
    e.사원번호,
    e.사원명,
    e.부서코드,
    (SELECT MAX(s.급여) 
       FROM emp s 
      WHERE s.사원번호 = e.사원번호) AS 최근급여,
    d.부서평균급여
FROM emp e
JOIN dept_avg d ON e.부서코드 = d.부서코드
WHERE e.부서코드 LIKE 'Z%';

```


지금 구조는 부서 평균 급여를 사원 행마다 다시 계산하기 때문에 성능이 비효율적입니다.<br>
→ 부서 평균은 CTE(Common Table Expression)나 GROUP BY로 먼저 계산 후 JOIN 하는 방식이 훨씬 효율적
