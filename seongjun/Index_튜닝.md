# 3.1 테이블 액세스 최소화

## 테이블 랜덤 액세스 절차
- **인덱스 스캔 후 ROWID 획득**: 쿼리문에 사용하는 컬럼을 인덱스가 모두 포함하는 경우가 아니라면, 인덱스를 스캔한 후에 ROWID 획득.
- **버퍼 캐시 우선 탐색**: ROWID가 가리키는 테이블 블록을 버퍼 캐시에서 먼저 찾아봄.
- **디스크 읽기**: 못 찾을 때만 ROWID를 가지고 디스크에서 찾아 블록을 읽는다.
- **중요 포인트**: 1장에서 설명했지만, 디스크에서 읽는 방법은 엄청 느리지만, 버퍼 캐시를 탐색하는 것도 생각보다 고비용 구조이므로 **테이블 랜덤 액세스 수 자체를 줄여야 함.**

## 클러스터링 팩터(CF)
- **정의**: 같은 값을 갖는 데이터끼리 물리적으로 모여있는 정도
- **효과**: 높을수록 데이터 찾는 속도가 빠르다
- **왜 빠른가?**
  - 어차피 인덱스로 스캔한 수만큼 테이블을 액세스 할 텐데 CF가 좋다고 빠른 이유는 무엇일까?
  - **버퍼 Pinning**: ROWID로 테이블을 액세스 할 때, 아주 어렵게 얻은 테이블 블록에 대한 포인터를 바로 해제하지 않고 가지고 있음.
  - 다음 데이터를 테이블 액세스 하려고 ROWID를 확인해보니, 이전 스캔한 ROWID와 같은 테이블 블록임.
  - 그럼 테이블 블록 포인터를 얻기 위한 노력을 다시 할 필요가 없이, 이전 포인터를 그대로 사용하면 되기 때문에 **CF가 좋으면 블록 I/O가 적게 발생**하여 찾는 속도가 빠름.

## 인덱스 손익분기점
- **정의**: Index Range Scan이 Table Full Scan 보다 느려지는 조회 건수 지점
- **특징**
  - Table Full Scan으로 스캔할 경우, 어떤 쿼리든 동일한 성능을 가짐.
  - Index Range Scan은 조회되는 건수가 많아질 경우 점점 느려짐.
  - 이 값은 CF가 나쁘면 손익분기점은 **최악의 경우 5%** 정도가 되고 아주 좋으면 **90%** 수준으로 올라간다.
  - **테이블의 로우수가 많을수록 손익분기점은 더욱 낮아진다.**
  - 스캔하려는 건수가 **1만 건만 돼도** Table Full Scan이 빠를 수 있다.

## 인덱스 컬럼 추가
- **아이디어**: 해당하는 인덱스가 없다고 새로 만드는 것보다, 기존 인덱스에 추가하는 것도 효과적일 수 있음
- **사례**
  - *부서번호 + 업무 인덱스*에서 **부서번호 + 연봉**으로 검색 → 부서번호에 해당하는 데이터가 많으면 랜덤 액세스가 많음
  - *부서번호 + 업무 + 연봉 인덱스*에서 **부서번호 + 연봉**으로 검색 → 스캔량은 동일하여도 **랜덤 액세스는 적음**
- **커버링 인덱스**: 조건절에 해당하는 컬럼이 모두 인덱스에 존재하지만 다른 컬럼이 필요해 테이블 액세스를 해야 한다면, 해당 컬럼을 인덱스에 추가하는 방법도 있다.

```sql
-- 인덱스 : 부서번호 일 경우, 부서번호로 테이블 스캔을 하지만, 수량을 위해서 테이블 액세스 필요
-- 인덱스 : 부서번호 + 수량일 경우, 수량이 인덱스 자체에 있으므로, 테이블 액세스 불필요
SELECT 부서번호, SUM(수량)
FROM 판매집계
WHERE 부서번호 LIKE '12%'
GROUP BY 부서번호;
```
## 인덱스 구조 테이블 (IOT)
- **정의**: 랜덤 액세스가 절대 발생하지 않도록 인덱스 자체에 테이블 데이터를 갖는 방식.
- **사용법**: Index-Organized Table(IOT). 테이블 생성 시 `ORGANIZATION INDEX` 옵션 사용.
- **특징**: 데이터가 키 순으로 정렬 상태 유지 → **클러스터링 팩터(CF)가 좋음** → BETWEEN/부등호로 넓은 범위 읽기에 유리.
- **예시**
  - (PK: 사번, 일자) 구조에서 일별로 실적 100건씩 Insert → 동일 사번의 실적이 물리적으로 분산(CF 나쁨).
  - 아래 쿼리는 여러 블록 I/O를 유발:
    ```sql
    SELECT *
    FROM 실적
    WHERE 사번 = 'S1234'
      AND 일자 BETWEEN '20200101' AND '20201231';
    ```
  - **IOT 전환 효과**: (사번, 일자) 순으로 정렬 유지 → 동일 키 데이터가 **같은/인접 블록**에 밀집 → **블록 I/O 감소**.

## 인덱스 클러스터 테이블
- **정의**: 클러스터 키(예: 부서번호) 값이 같은 레코드를 한 블록에 모아 저장.
- **효과**: 인덱스 스캔 시 **값 하나당 랜덤 액세스 1회** → 동일 키 데이터가 많을 때 효율적.

```sql
-- 인덱스 클러스터 생성
CREATE CLUSTER c_dept# (deptno NUMBER(2)) INDEX;

-- 클러스터 인덱스 생성
CREATE INDEX c_dept#_idx ON CLUSTER c_dept#;

-- 클러스터 테이블 생성
CREATE TABLE dept (
  deptno NUMBER(2) NOT NULL, ...
) CLUSTER c_dept#(deptno);
```

## 해시 클러스터 테이블
- 정의: 인덱스 대신 특정 키에 대한 해시 알고리즘으로 클러스터를 직접 찾음.
- 효과: 해시 값 하나당 랜덤 액세스 1회.
```sql
-- 해시 클러스터 생성
CREATE CLUSTER c_dept# (deptno NUMBER(2)) HASHKEYS 4;

-- 클러스터 테이블 생성
CREATE TABLE dept (
  deptno NUMBER(2) NOT NULL, ...
) CLUSTER c_dept#(deptno);
```

# 3.2 부분 범위 처리 활용
## 개념
- 부분 범위 처리: 클라이언트로 데이터를 한 번에 쏟지 않고, Fetch Call마다 일정량씩 전송.
- 장점: 대상 레코드가 많아도 매우 빠른 초기 응답 가능.

## 실무 포인트

- Java fetchSize: 불필요한 전송 최소화되도록 조절(너무 작으면 Fetch Call 과다).
- ORDER BY + 인덱스 정렬 일치: 인덱스가 정렬을 보장하므로 SORT 생략 → 일부만 즉시 Fetch 가능.

# 3.3 인덱스 스캔 효율화
## 용어
- 인덱스 액세스: 인덱스 스캔 범위를 결정하는 조건.
- 인덱스 필터: 테이블로 액세스할지 여부를 결정.
- 테이블 필터: 결과 포함/다음 단계 전달 여부 결정.
```sql
-- 인덱스 (C1, C2, C3, C4)
-- 1) C1~C4 모두 액세스 조건
SELECT * FROM A WHERE C1='' AND C2='' AND C3='' AND C4='';

-- 2) C1~C3 액세스, C4는 인덱스 필터
SELECT * FROM A WHERE C1='' AND C2='' AND C3 BETWEEN '' AND '' AND C4='';

-- 3) C1만 액세스, C2~C4는 인덱스 필터
SELECT * FROM A WHERE C1 BETWEEN '' AND '' AND C2='' AND C3='' AND C4='';

```
- 주의(오라클 실행계획): 모두 ‘인덱스 액세스’로 표기될 수 있음 → 개념 구별 필요.
- 비효율 규칙
  - 뒤쪽 컬럼이 조건에 없거나 등치가 아니어도 비효율 아님.
  - 선행 컬럼이 없거나 **범위 조건(BETWEEN, >, <)**이면 비효율 발생.

## BETWEEN → IN-List 전환
- 상황: 선행 컬럼에 BETWEEN이 필요하고 인덱스 변경 불가.
- 대안: BETWEEN을 IN으로 바꾸면 옵티마이저가 INLIST ITERATOR(UNION ALL) 사용.

```sql
-- 인덱스: (부서번호, 연봉)

-- 비효율: 선행 컬럼 BETWEEN
SELECT 부서번호, 연봉
FROM 사원
WHERE 부서번호 BETWEEN '1' AND '2'
  AND 연봉 = '4000';

-- 대안: IN (옵티마이저가 UNION ALL 형태로 전개)
SELECT 부서번호, 연봉
FROM 사원
WHERE 부서번호 IN ('1','2')
  AND 연봉 = '4000';

```
- IN 값 관리: 값이 많아지면 관리 어려움 → NL 조인으로 코드 테이블에 범위를 위임.
```sql
SELECT /*+ ordered use_nl(B) */
  B.부서번호, B.연봉
FROM 코드 A, 사원 B
WHERE A.코드값 = '사원번호'
  AND A.코드 BETWEEN '1' AND '5'
  AND B.부서번호 = A.코드
  AND B.연봉 = '4000';
```
- 주의: In-List는 값 개수만큼 수직 탐색이 추가 → 근접한 레코드면 오히려 느릴 수 있음.
- 대안: INDEX_SS 힌트로 Index Skip Scan 유도.

## IN은 '='이 아니다
- IN이 '='로 동작하려면 옵티마이저가 IN-List 전개를 해야 함.
- 전개가 없으면 IN은 필터 조건으로만 사용.
- 제어 힌트: NUM_INDEX_KEYS로 인덱스 사용 컬럼 수 지정.
```sql
-- 인덱스: (고객번호, 상품ID)
-- num=1 → 고객번호까지만 인덱스, 상품ID는 필터
SELECT /*+ NUM_INDEX_KEYS(TABLENAME INDEXNAME 1) */ *
FROM TABLENAME
WHERE 고객번호 = :cust_no
  AND 상품ID IN ('1','2','3');

-- num=2 → 상품ID까지 인덱스 사용 → IN-List 전개
SELECT /*+ NUM_INDEX_KEYS(TABLENAME INDEXNAME 2) */ *
FROM TABLENAME
WHERE 고객번호 = :cust_no
  AND 상품ID IN ('1','2','3');
```

## LIKE vs BETWEEN
- BETWEEN 선호: 시작/끝을 명확히 알고 한 번의 스캔으로 처리.
- LIKE 특성: 경계 보정 때문에 앞/뒤 추가 스캔이 생길 수 있음.

## LIKE/BETWEEN 남용 주의
```sql
-- 인덱스: (사원번호, 이름, 주소)
-- 옵션 처리 편의를 위해 LIKE 사용 → 대량 데이터에서 인덱스 비효율
SELECT *
FROM 사원
WHERE 사원번호 = :no
  AND 이름 LIKE :name || '%'
  AND 주소 LIKE :addr || '%';

```
- 많은 데이터에서는 옵션 조합별로 '=' 중심 쿼리 분기를 고려(귀찮아도 성능 우선).

## 선두 컬럼 OR 사용 주의
```sql
-- 인덱스: (사원ID, 이름)
-- 선두 컬럼에 OR → 인덱스 사용 불가 케이스 발생
SELECT *
FROM 사원
WHERE (:id IS NULL OR 사원ID = :id)
  AND 이름 BETWEEN :name1 AND :name2;

```
## 후행 컬럼의 LIKE/BETWEEN
- 필수(선행) 조건의 선택도가 좋을 때는 후행 컬럼의 LIKE/BETWEEN도 성능 양호.

```sql
-- 인덱스: (상품명, 상품분류코드) - 상품명 선택도 좋음
SELECT *
FROM 상품
WHERE 상품명 = :nm
  AND 상품분류코드 LIKE :cd || '%';

-- 인덱스: (상품대분류코드, 상품코드) - 대분류 선택도 낮음
-- 상품코드 미입력 시 액세스량 과다
SELECT *
FROM 상품
WHERE 상품대분류코드 = :big_cd
  AND 상품코드 LIKE :cd || '%';

```

## LIKE/BETWEEN 튜닝 위치 체크리스트
- 인덱스 선두 컬럼에 배치.
- NULL 허용 컬럼: 실제 NULL 입력 시 결과에서 누락 주의.
- 숫자형 컬럼: LIKE 사용 시 문자열 변환 → 인덱스 미사용 가능성.
- 가변 길이 컬럼: 패턴 매칭 비용 고려.

# 3.4 인덱스 설계
### 인덱스가 많으면 생기는 비용
- DML 성능 저하, DB 사이즈 증가, 운영/관리 비용 상승.

### 기본 설계 원칙
- 항상/자주 조건절에 쓰는 컬럼 선정.
- '=' 조건으로 자주 조회되는 컬럼을 앞쪽에 둔다.

### 추가 고려 요소
- 수행 빈도, 업무 중요도, 클러스터링 팩터, 데이터량,
- DML 부하, 저장 공간, 관리 비용 등.

### NL 조인 고려
- NL 조인의 Inner 쪽은 여러 번 호출됨 → '=' 조건 선두 인덱스로 최대한 인덱스 타도록 설계.

## 현실적인 전략
- 특정 쿼리군에 일자 BETWEEN과 여러 '=' 조건이 혼재:
  - 일자를 선두 컬럼으로 하고 나머지 '=' 조건을 후행에 둔 인덱스 1개.
  - 가장 자주 쓰는 '=' 조건을 선두로, 일자를 후행으로 둔 인덱스 보조 1개.

### 소트 생략(ORDER BY 최적화) 인덱스 공식
1) '=' 조건 컬럼을 선두에.  
2) ORDER BY 컬럼을 그 다음에.  
3) 나머지 범위 조건 컬럼은 분포를 보고 포함 여부 판단.

### 결합 인덱스 선택도
- 인덱스 컬럼을 모두 '='로 조회했을 때 전체 대비 선택 비율.
- 선택도 높음(= 넓게 잡힘) → 테이블 액세스가 많아져 비효율 → 인덱스 이점 낮음.

### 중복 인덱스 제거
- 완전 중복: 앞에서부터 동일하게 포함된 인덱스가 있으면 작은 인덱스 제거.
- 불완전 중복: 선두 동일, 2번째 이후 다름. 선두 컬럼 카디널리티가 매우 낮으면(≈ ≤5) 하나로 합치는 것이 유리.
